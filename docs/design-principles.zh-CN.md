# 产品设计原则

2026-10-18，用户明确要求：**技术细节上精简，不向用户展示不必要的技术说明。**

界面围绕学习内容和操作结果组织。让用户知道正在看什么、可以做什么、结果怎样；框架、引擎、内存、线程、坐标、开发验证和迁移阶段留给维护文档。

删除没有决策价值的说明，简化重复标签。正常操作通过控件变化反馈，不在状态栏解释内部工作。出现失败时，只给出用户能理解的原因与可执行的下一步。

| 避免 | 采用 |
| --- | --- |
| 12页来源标签、500道题目压力样例 | 删除；需要计数时只显示“500道题” |
| 答案 · 本次会话编辑 | 答案 |
| 来源 · 合成原件第1页（重复显示） | 删除重复项；确有来源需要时在一处显示页码 |
| 来源区域使用同一坐标变换 | 删除，直接呈现旋转结果 |
| PDFium后台渲染、内存页面、编译绑定、AOT | 不在产品界面展示 |
| 编辑已保留在内存中，资料库保存尚未接入 | 尚未保存 |

保持真实：示例用一次“示例资料”标明；不能保存就明确说明修改不会保存。必要的文件大小、页数限制在操作失败时提示，不常驻展示实现细节。未完成的能力不放置伪装为可用的入口。

布局随内容收缩。空反馈、空列表和未使用的网格行不预留位置，不用无关的最小高度撑大卡片。标题、字段、按钮与卡片边缘保持统一的间距和对齐；小窗口下换行或改为单列，不能靠截断操作名称或挤掉字段来适配。

本原则覆盖默认页面、设置、菜单、关于、提示、状态、错误及辅助功能文案。开发与验收文档保留必要技术信息，供维护者接续。

窗口与顶部导航参考Microsoft Store等Windows原生软件：标题区融入应用，应用标识只出现一次，控件间距、字体、悬停和主题保持统一。拖动、最大化/贴靠及窗口按钮保留系统行为，不额外绘制一套仿制按钮；不为模仿参考图添加尚无实际功能的搜索、账户等入口。

## 每次 UI 修改后的视觉验收（强制）

2026-10-18，用户明确要求：**每次 UI 修改后都必须实际渲染、视觉检查并打磨每一个细节；视觉效果必须完美，符合最佳实践、符合人类直觉。** 此要求适用于全部界面改动，包括只改一处文案、间距、选项或控件状态的小改动。

1. 运行修改后的实际应用，查看受影响页面和关联区域的真实界面或实际渲染截图。源码审查、布局参数、设计稿、构建与自动化测试均不能代替这一步。
2. 检查所有可见细节，包括但不限于多余留白、不合理布局、重复信息、过大或过小的间距、对齐偏差、字体和视觉层级不统一、文字截断与换行、内容溢出、控件尺寸及状态反馈。沿用 Windows 原生界面与 Fluent 设计最佳实践，让信息顺序、操作位置和反馈符合人类直觉。
3. 按受影响内容检查适用的空、单项、多项、长名称或长文本、错误反馈、深浅主题及宽窄窗口状态；交互变化还应检查相关的选中、禁用、悬停和焦点状态。检查范围必须覆盖改动可能影响的相邻区域，不能只裁取局部来掩盖整体布局问题。
4. 对发现的每一个细小问题进行修复，然后重新渲染并复查受影响状态，循环打磨，直到没有任何已发现但未修复的视觉问题。功能可用与视觉质量同时达标才能认定完成，不因问题细小而跳过。
5. 在维护记录中写明检查范围、实际渲染或截图证据、修复结果和未验证项。无法完成实际渲染检查时，明确记录视觉验收未完成，不得宣称界面已通过验收。
